## 1. 需求背景和已完成验证

现有「答讯 · ReplyNotice」已经在 ChatGPT 回答完成时于本机创建 Windows/Edge 原生通知，具备尽可能延长停留、通知正文点击、单条“关闭”、批量“清空全部”、问答摘要等功能。

用户经常在 XF、工位电脑、105 等多台电脑间切换远程窗口，即使 XF 的 ChatGPT 完成回答，本机通知仍可能不可见。目标是让**任意安装答讯且 Edge 正在运行的电脑**接收其他电脑的完成提醒，无需保持远程桌面在前台。

已由用户手动验证：
- `https://ntfy.sh/app` 可以订阅和发布 `daxun-test-1` 测试主题；
- 两台电脑订阅同一主题后，接收端可实时看到发送消息；
- 接收电脑 Edge 最小化，切回时消息已自动出现，无需手动刷新。

**注意：上述验证针对 ntfy 网页客户端，不等于答讯扩展 Service Worker 的 WebSocket 长连接已经验证。** 本机 ntfy 网站通知的 `GRANT NOW` 授权曾未生效，但不阻碍消息中转测试；正式方案由答讯扩展调用 `chrome.notifications`，不依赖 ntfy 网页通知权限。

## 2. 最终架构（第一版范围）

```text
XF 电脑（Edge + 答讯） ─┐
工位电脑（Edge + 答讯） ├─ HTTPS 发布 / WebSocket 订阅 ── ntfy.sh 公共主题
105 电脑（Edge + 答讯） ─┘                 │
                                          └─ 各接收端调用本机 chrome.notifications.create()
```

- **发送端和接收端均为同一套答讯扩展**，角色由本地“允许发送”“允许接收”两个独立开关决定；任意电脑可同时启用两项。
- **中转仅用 ntfy.sh**：不自建服务、不要求 Tailscale、不要求同一局域网、不运行额外 Windows 接收进程。
- **接收端仅要求 Edge 运行**，可最小化、无须打开 ChatGPT 页面；如果 Edge/其后台进程彻底退出、电脑睡眠/离线，则不保证实时接收。
- 不需要保持 ntfy 网页客户端打开；正式由答讯自己的后台模块订阅。
- 原有 Windows 本机通知的行为不变；远程消息到达后在**接收电脑本地**生成另一条 Windows 通知。
- **关闭/清空操作只作用于当前电脑**，不向其他电脑广播清理事件，不影响源电脑的通知。

### 2.1 最终用户交互

| 场景/操作 | 来源电脑的本地通知 | 其他电脑收到的远程通知 |
| --- | --- | --- |
| ChatGPT 正常回答完成 | 按原逻辑显示 | 开启接收后显示 |
| 标题 | `答讯 · ReplyNotice` | `答讯 · ReplyNotice` |
| 正文 | 原有提问摘要 + 回答摘要，受原预览开关控制 | 与发送电脑**实际生成的本机通知正文一致**，额外标记来源电脑 |
| 问题截断 | 现有逻辑，约前 50 字 | 直接复用相同结果 |
| 回答截断 | 现有逻辑，约前 100 字 | 直接复用相同结果 |
| 通知尽可能常驻 | 保留 `requireInteraction: true` | 同样保留，受 Windows/Edge 限制 |
| 点击左侧“关闭” | 只关闭该条 | 只关闭该条 |
| 点击右侧“清空全部” | 清空本机答讯可管理的通知 | 清空**接收电脑本机**答讯可管理的通知 |
| 点击通知正文 | 保持当前行为：在来源电脑打开对应 ChatGPT 会话，并清除本条 | **只关闭本条，不打开 ChatGPT 或任何网页** |
| 系统右上角 X | 只关闭本条 | 只关闭本条 |
| 其他电脑关闭或清空 | 不受影响 | 不同步状态 |

来源电脑名称（例如 `XF`）可在远程正文最前面增加 `来源：XF\n`，后续正文与来源电脑相同。Windows 按钮实际排版由系统决定，不要求严格 50/50。

## 3. 配置与隐私约束

建议在插件设置页增加：

| 配置 | 含义 | 默认 |
| --- | --- | --- |
| 跨电脑发送 | 本机回答完成后发布到 ntfy | **关闭** |
| 跨电脑接收 | 订阅 ntfy 主题并创建本机通知 | **关闭** |
| 设备名称 | XF / 工位电脑 / 105 等标识 | 用户配置 |
| 设备 ID | 本机随机生成的稳定唯一 ID，用于防自回环 | 首次启用生成并本地持久化 |
| 通信主题 | 所有需同步电脑使用同一个 ntfy 主题 | **空值，须用户配置** |
| 允许远程传输问答摘要 | 明确授权把本地通知里的提问/回答摘要传到第三方 ntfy.sh | **关闭，需主动开启** |

- **正常显示规则：** 当来源电脑本机问答预览开启，且“允许远程传输问答摘要”也已开启时，跨电脑传输**来源电脑已格式化的本地通知正文**；接收端原样使用，仅追加来源电脑标记。
- 当来源电脑本地预览关闭时，本地和远程均使用现有的通用完成文案；不能因为跨电脑选项开启就泄露摘要。
- 若来源电脑开启本地预览、但**未**明确授权跨电脑传输问答摘要，远程只传通用完成提醒。这是“内容一致”的**隐私例外**，设置界面需要明确说明。
- 不发送完整聊天记录、不上传会话 URL、不发送登录令牌、Cookie 或本机文件，不因为远程接收而产生额外 ChatGPT 页面访问。
- `daxun-test-1` **只能用于测试**；正式主题必须替换为高熵随机标识（建议至少 128 bit 随机性，不在源码中硬编码）。
- **重要安全边界：** ntfy.sh 公共匿名主题不是经过身份认证的私有通道；随机主题只是降低被猜测概率，**不是端到端加密或真正的访问控制**。问答摘要会经过 ntfy.sh 服务商，且知晓主题者可能订阅/发布消息。不要传输敏感的工作、个人或保密信息；正式启用摘要同步前应先接受该限制。
- 建议发布时使用 ntfy 的不缓存选项（例如 `X-Cache: no`；实现前依当前官方文档核对），减少服务器留存。但**不缓存并不等于端到端加密或保证服务端零留存**；也意味着断线期间消息可能丢失。
- 配置仅保存在各台电脑的扩展本地存储，避免写入代码仓库、浏览器同步或日志；远程事件/服务端数据均按**不可信输入**处理。

## 4. 消息模型和数据流

### 4.1 消息体（示意协议 v1）

推荐 **HTTPS 发布纯文本 JSON 消息**（JSON 字符串作为 `POST https://ntfy.sh/<topic>` 请求体），接收端从 ntfy WebSocket 的 `event: "message"` 消息中读取外层 `message` 字段再解析为以下对象。采用此方式可避免与 ntfy“向根路径 POST JSON 发布”接口混淆；代码实现需以 ntfy 官方文档为准。

```json
{
  "protocol": "replynotice-sync",
  "schemaVersion": 1,
  "type": "reply_done",
  "eventId": "随机唯一事件ID",
  "deviceId": "随机稳定设备ID",
  "deviceName": "XF",
  "timestamp": 1794800000000,
  "title": "答讯 · ReplyNotice",
  "message": "问：……\n答：……"
}
```

- `message` 为来源电脑本地通知的**最终展示文本**，而不是未经截断的完整问答；如未授权远程摘要传输，改为通用完成提示。
- `timestamp` 为毫秒 Unix 时间；不要直接拿 ntfy 外层的秒级 `time` 当作毫秒比较。
- `eventId` 每轮回答唯一；`deviceId` 与机器绑定而非浏览器标签 ID；不可仅靠 `cycleId` 跨机器去重。
- 对上述字段做严格类型、长度与格式校验；例如 `deviceName` 以及 `message` 限长，限制不可见控制字符。未经校验的远程消息不能触发导航或修改用户设置。
- 外部可向公共主题发送伪造消息，客户端协议校验**不能证明来源身份**。第一版以随机主题 + 最小数据为前提，不声称具备可靠身份认证；如需抗伪造，需要后续独立的签名/认证设计。

### 4.2 发送路径

1. 继续使用 `content.ts` 已有 `CHATGPT_REPLY_DONE` 完成事件，不重新探测 DOM。
2. `background.ts` 对当前回答进行**一次去重和可信发送者校验**，避免异常站点触发通知。
3. 获取本机通知开关、预览设置、跨电脑发送开关、摘要共享开关和通信配置；生成本机通知与待发布正文。**本机通知开关关闭，不应该阻止跨电脑发送**。
4. 对开启了跨电脑发送的电脑，使用 `fetch` 向 ntfy 主题发送一次消息，设置请求超时和简洁错误日志。不要阻塞原有本机通知，也不要因发送失败影响 ChatGPT。
5. 对来自远程 WebSocket 的消息仅创建本地通知，**绝不重新发布**，防止循环转发。
6. 测试通知另设测试路径；不得将 `CHATGPT_TEST_NOTIFICATION` 的本地诊断请求误当成正常回答广播，除非有明确的跨电脑测试控制。

### 4.3 接收路径

1. 开启跨电脑接收且主题配置有效时，`background.ts` 在扩展后台订阅 `wss://ntfy.sh/<topic>/ws`。
2. 只处理 ntfy 外层 `event === "message"`；忽略 `open`、`keepalive` 等协议事件。
3. 验证内部 `protocol/schemaVersion/type`，并检查时间戳与长度；不接受陌生或过旧的消息。
4. **收到来源 `deviceId` 与本机相同的事件直接跳过**，避免自己发送又自己接收。
5. 同一个 `eventId` 只显示一次，维护有界短期去重记录，避免重连/事件重复造成多条弹窗。
6. 接收电脑的**Windows 系统通知开关**仍然决定是否显示本机弹窗；跨电脑“允许接收”只决定是否订阅，不强制打开系统通知。
7. 接收端使用现有 `createSystemNotification()` 统一创建通知，保留 `requireInteraction` 和双按钮。
8. **显式标记远程通知 ID 的类型**，正文点击进入“仅关闭”分支；不能因为找不到来源 `NotificationOrigin` 而沿用当前本地点击的 `HOME_URL` 回退逻辑。Service Worker 重新启动后也必须能辨识远程通知类型。

### 4.4 保活、重连、旧消息

- Windows/Edge 前台或后台运行均应尝试维持连接；浏览器彻底退出/机器睡眠期间**不保证**通知实时到达。
- Chrome 116+ 的 Manifest V3 扩展 Service Worker 支持 WebSocket；连接保活需根据 Chrome 以及 ntfy 的实际协议测试，不能仅仅创建 WebSocket 就认定后台常驻。
- 推荐每约 **20 秒**以内有可验证的 WebSocket 交互或保活机制；应确认其与 ntfy 服务器协议兼容，**不得未经验证随意发送文本心跳**。
- `onclose` / `onerror` 时有限退避重连（例如 1s → 2s → 5s → 10s → 最大 30s，增加抖动），停用接收或切换主题时停止旧连接和定时器，避免重复连接与持续资源消耗。
- **第一版只接收新事件，不主动补弹历史积压**；避免使用 `since=all` 或无界历史回放。通过有界去重及新鲜度过滤（例如允许不超过 2 分钟的事件）避免恢复时弹旧通知。
- 如果断线期间错过了事件，允许丢失，先确保正常实时链路的轻量和可靠；不引入数据库、持久化队列或复杂补发机制。

## 6. 设置与故障行为验收表

| 验收场景 | 预期结果 |
| --- | --- |
| XF 与工位电脑均安装答讯、Edge 运行且使用同一正式随机主题 | XF 完成回答：本机和接收端分别创建一次通知 |
| XF 也开启“跨电脑接收” | 不重复收到自己广播的相同提醒 |
| 工位电脑开启发送和接收，随后回答完成 | 其他电脑同样收到；不存在 XF 固定唯一发送端 |
| 本机 Windows 通知关闭、跨电脑发送开启 | 本机不弹窗；其他接收端仍能收到 |
| 接收端 Windows 通知关闭、跨电脑接收开启 | 不强制创建本机 Windows 通知 |
| 本机预览和跨电脑摘要共享都开启 | 远程正文与来源本机通知正文一致，附带来源电脑名称 |
| 本机预览关闭 | 本机和远程均显示通用完成提示，不泄露摘要 |
| 本机预览开启但跨电脑摘要共享关闭 | 本地可预览，远程仅通用提醒（隐私例外） |
| 远程通知正文点击 | **只清除本条，不打开任何网页** |
| 本地通知正文点击 | 原有会话跳转功能不变 |
| 远程通知“关闭” / “清空全部” | 仅处理当前电脑答讯的单条 / 全部通知 |
| 在一台电脑清空 | 其他电脑已存在的通知不受影响 |
| 同一事件重复传入或重新连接 | 不应重复弹窗 |
| 突然断网、恢复网络、Edge 最小化 | 能按既定策略重连并恢复接收；无旧消息洪泛 |
| Edge 退出或电脑睡眠 | 允许漏收；重新打开后不集中补弹大量旧消息 |
| 通信主题填错、为空、权限不足、服务限流 | 明确提示/日志，不影响本地原功能，无无限重试风暴 |
| 第三方向主题发送格式错误或伪造内容 | 非法消息拒绝；符合格式的伪造消息仍存在公共主题风险，不宣称已认证 |
| ntfy 网站的 GRANT NOW 未授权 | 不影响扩展自己的 Windows 通知 API（须单独验证扩展通知权限） |
| 扩展重载 / Service Worker 恢复 | 接收开关仍生效，远程点击关闭类型不丢失 |
| `pnpm build`，Edge 重新加载 | 构建成功，插件版本为 2.0.5，本地 v2.0.4 功能不回归 |

可按“单电脑发布验证 → 两电脑实时 → 双向收发 → 本地/远程点击行为 → 后台运行与断线恢复 → 多电脑回归”的顺序验收。

## 7. 明确不做

- 不开发手机推送；iPhone/安卓推送需求暂缓。
- 不要求运行 Tailscale、自建 ntfy、WebCodex 或额外 Windows 客户端。
- 不同步通知的关闭、清空和已读状态。
- 不传输会话 URL、不在远程电脑点击通知时打开 ChatGPT。
- 不跨电脑传输完整聊天记录、附件或敏感数据。
- 不做历史补发、离线数据库、跨设备排队和额外管理后台。
- 不保证 Edge 完全退出、系统休眠、网络中断情况下的通知实时送达。
- 不因为接收端问答摘要设置不同而强制重新提取或改写来源文本；按**发送端最终格式化正文**展示。
