# 答讯 · ReplyNotice — v2.0.1 需求与修改方案

## 一、基本信息

- 仓库：`LynFrost/Daxun`
- 开发分支：`feature/v2.0.1`
- 基线版本：v2.0.0（已合并至 `main`）
- 目标版本：v2.0.1
- 本轮范围：修复 ChatGPT 新页面 DOM 结构导致的**回答完成后不弹出 Windows 系统通知**
- 当前状态：**仅记录修改方案，尚未实施代码更改或完成 v2.0.1 验证**

## 二、已复现的问题和证据

### 2.1 现象

- 在 Edge 安装答讯 v2.0.0，且 System Notification 开启的情况下，ChatGPT 普通回答结束后未出现 Windows 通知。
- 通过插件开发者工具直接发送 `CHATGPT_TEST_NOTIFICATION`，后台返回 `{status: 'created'}`、无 API 错误，并且 Windows **实际弹出通知**。因此本次优先排查内容脚本的回答完成检测，而不是改动已经验证可用的后台通知通道。
- ChatGPT 页面的 Console 出现 `[ReplyNotice/content] Tracking reply cycle ... composer submitted`，随后出现 `No confirmed reply completion yet`，且 `activeSeen: false`、`assistantFound: false`、`completionActionFound: false`。

### 2.2 当前 ChatGPT 页面真实 DOM（已由 Edge Console 只读检查）

| 检查项 | 结果 |
| --- | --- |
| 旧用户标记 `[data-message-author-role="user"]`、`[data-role="user"]` | 0 |
| 旧助手标记 `[data-message-author-role="assistant"]`、`[data-role="assistant"]` | 0 |
| 旧 `conversation-turn-` 与 `data-turn` 标记 | 0 |
| `[data-turn-key]` 轮次容器 | 1 个（该次采样） |
| `[data-conversation-role]` | 1 个，其值为 `assistant`，元素为 `H4` |
| `[data-chatgpt-agent-turn-start]` | 轮次容器内 1 个 |
| Copy 回复按钮 | 轮次容器内 1 个 |
| `[data-is-streaming="true"]`、旧 Stop/Spinner 等活动标记 | 完成后采样为 0；**不能据此判定生成过程中的实际状态** |

已确认 Copy 按钮和 `H4[data-conversation-role="assistant"]` 属于同一个 `DIV[data-turn-key]`。因此应识别**整个助手轮次容器**，而非仅识别角色标题 `H4`。

## 三、修改方案（先做最小修复）

### 3.1 修改位置

- 文件：`entrypoints/content.ts`
- 基于 v2.0.0 的位置：**原第 102 行**（以实际文件内容为准）
- 只替换 `ASSISTANT_SELECTOR` 常量定义；优先不改后台、声音、UI、去重及通知消息格式。

**修改前：**

```typescript
const ASSISTANT_SELECTOR = '[data-message-author-role="assistant"], [data-role="assistant"]';
```

**修改后：**

```typescript
const ASSISTANT_SELECTOR = [
  '[data-turn-key]:has([data-conversation-role="assistant"])',
  '[data-message-author-role="assistant"]',
  '[data-role="assistant"]',
].join(',');
```

### 3.2 修改理由

1. `[data-turn-key]:has([data-conversation-role="assistant"])` 匹配本次实测的**助手回复容器**，可让 `findResponse()` 找到回答，并让 `responseSignature()` 跟踪其内容变动。
2. 旧选择器仍保留作兼容性兜底。
3. `hasCompletionAction()` 原逻辑能够在该轮次容器内查找 Copy 按钮，无须为本次最小修复更改。
4. 当前 `hasNewResponse` 已包含“新助手容器不同于本轮基线”的条件；即使此次未捕获到旧的活动标记，在新容器确实生成、Copy 完成操作出现且内容保持静默时，仍有机会触发通知。
5. 保留既有约 2.5 秒静默确认、响应周期去重、错误日志及系统通知开关逻辑。

**注意：** 上述方案能够解释目前普通回答的失败根因，但属于**待验证的最小修复假设**，不是对复杂思考/工具调用、已有轮次容器被复用、虚拟化渲染或未来 DOM 变化的全面保证；不应仅因静态 DOM 匹配就宣称所有场景已修复。尤其现有 `USER_SELECTOR` 仍无法匹配本次采样的用户元素，依赖提交事件开始跟踪；应在实测时关注新一轮回复和连续多轮回复。

## 五、验证与验收

### 5.1 构建和安装

1. 在 `feature/v2.0.1` 实施代码修改后运行 `pnpm build`，确认构建通过。
2. 在 `edge://extensions` 重新加载本地未打包扩展（`.output/chrome-mv3`）。
3. 刷新 ChatGPT 页面，确保新内容脚本生效；仅保留一个答讯实例，避免双重通知。
4. 在 ChatGPT 网页 DevTools Console 启用 Verbose，观察 `ReplyNotice` 日志。

### 5.2 核心验收场景

| 场景 | 预期 |
| --- | --- |
| 新发起的一次简短回答 | 最终完成后出现一次 Windows 系统通知 |
| 网页 Console 日志链路 | 依次出现 `Tracking reply cycle`、`Final reply detected`、`Background completion result: created` |
| 连续两轮新问题 | 每轮仅通知一次，不漏报、不串轮 |
| 已完成回答后刷新页面 | 不误通知 |
| 关闭 System Notification | 回答完成后不创建系统通知 |
| 切换其他 Edge 标签页、最小化 Edge | 回答完成后仍能通知（在系统允许显示时） |
| 长时间思考、工具调用、多阶段生成 | 不能提前通知；最终完成后仅通知一次 |

若普通回答仍失败，重点检查新容器何时出现、`baselineAssistant` 与 `assistant` 是否正确变化、Copy 按钮是否位于该容器，以及 `active` / `quietFor` 的状态。若普通回答通过但复杂场景失败，先保留诊断日志收集证据，再制定下一轮**最小增量**修复；不未经验证直接引入大规模 DOM 检测重构。
