## 2. 待修复问题

### 2.1 现象

- 目前答讯使用 Edge/Windows 的 `chrome.notifications` 原生通知，设置了 `requireInteraction: true`。
- 用户实测：桌面上最多悬停显示约 **3 条**；通知 1、2、3 保持占位后，新通知 4 及以后**无法正常出现在桌面横幅区域**。
- 用户可以接受**最多 3 条**，但不能接受旧通知长期占位导致新通知被阻塞。

### 2.2 确认的预期行为

**统一通知上限为 3 条；新通知到达时，先彻底删除最旧一条，再创建新通知。** 旧通知不保留在 Windows 通知中心，也不另建历史列表。

| 到达事件 | 保留的通知（按创建顺序） | 淘汰 |
| --- | --- | --- |
| 1 | 1 | 无 |
| 2 | 1、2 | 无 |
| 3 | 1、2、3 | 无 |
| 4 | 2、3、4 | 1 |
| 5 | 3、4、5 | 2 |
| 6 | 4、5、6 | 3 |

- **本机回答通知、跨电脑 ntfy 收到的通知、手动测试通知共用同一个容量 3**。
- 手动关闭一条后，新通知补充空位；不会为凑满 3 条重新显示旧通知。
- 现有 **“关闭”**、**“清空全部”**、正文点击跳转及问答摘要行为全部保留。
- 点击“清空全部”之后，新回答仍可正常产生新通知。
- **容量 3 是扩展可管理通知数量上限的目标**。Edge/Windows 桌面通知的展示顺序、动画及是否弹出横幅不由扩展完全控制；必须实机验证 `123 → 234 → 345` 的实际效果。

## 4. 待修复方案（选定）

### 4.1 基本方案

采用**单入口 FIFO + Chrome 通知 API 实际状态核对 + 串行创建/淘汰 + 会话级顺序记录**。

1. 所有通知继续通过现有 `createSystemNotification()` 创建。
2. 新增固定常量 `MAX_NOTIFICATIONS = 3`。
3. 在 `chrome.storage.session` 保存当前可管理通知 ID 的**创建顺序**，不保存问答正文。
4. 创建新通知前执行 `chrome.notifications.getAll()`，用真实存在的 ID 校正队列、剔除已删除的记录。
5. 若是**相同 ID 的通知更新**：不占新位置，不淘汰其他通知；更新后保留原位置（避免远程重投事件挤走新的通知）。
6. 若是**新 ID 且已有 3 条**：先 `clear()` 最旧通知；确认成功或该通知已经不存在，移除该 ID 的来源映射，再创建新通知。
7. 新通知创建成功后，将其 ID 追加到队列尾部并保存。创建失败则不能凭空增加队列项。
8. 对连续到达的通知使用**单个串行调度**，避免两条异步请求同时看到“还差一个空位”而突破容量；批量“清空全部”的执行也应和创建调度协调。
9. 发生 API 错误时不要无限重试：记录日志并安全失败；若无法确认已腾出名额，不应继续创建第 4 条。

### 4.2 容量与顺序定义

- 数量对象：**本扩展由 `chrome.notifications.getAll()` 返回的通知**，而不是 Windows 全局通知。
- 统一计数：本机回答、远程接收、诊断测试通知均计算在 3 条之内。
- 排序依据：首次成功创建并记录在本会话队列中的先后顺序，不用通知正文、标题或 ID 字典序猜测时间。
- 非本扩展的微信、Outlook、Windows 通知绝不清理。
- 遗留通知：新代码首次启动可能存在 v2.0.5 留下的旧通知，而它们没有新队列的时间戳。应在读取 `getAll()` 后显式对账；**没有可信排序就不能声称一定删的是最旧**。建议采用安全重置/确定性回退并记录日志，确保恢复至最多 3 条后再接收新通知。不要把任意 ID 排序伪装为真实创建顺序。
- `chrome.storage.session` 在同一浏览器会话内可帮助 MV3 Service Worker 恢复队列；浏览器彻底重启后，通知与队列状态的实际保留应按平台实测及上述对账规则处理。

### 4.3 串行原则

**必须等待最旧通知的清理结果，再尝试创建新通知。** 不允许“先 create 后 clear”，否则桌面已满时仍可能被 Edge 阻塞。

- 多条通知连续到达时，按进入通知创建队列的顺序处理。
- `clear()` 失败且通知仍存在时，不能宣称成功腾出空间；本次创建应报错/跳过，不制造第 4 条通知。
- `clear()` 返回 false 时，再用 `getAll()` 确认是否已不存在；不存在可视为已腾出空间。
- 避免把无关的通知发送到 ntfy 的动作塞入 FIFO 锁：跨电脑**发送**仍独立，只对**本机 Windows 通知创建/清理**进行排队。
- 后台 MV3 Service Worker 的运行期可能中断；状态恢复要依赖 session 存储和 `getAll()`，不能只保存于内存数组。

### 6.1 `entrypoints/background.ts`：常量区（约第 6–13 行）

const MAX_NOTIFICATIONS = 3;
const NOTIFICATION_QUEUE_KEY = 'replynotice_notification_queue';

### 6.2 `entrypoints/background.ts`：新增辅助函数（建议放在 `pruneOrigins()` 附近）

新增以下职责（可用最少的 2–4 个小函数实现，不要求按这些函数名逐个拆分）：

```typescript
// 逻辑示意
// 1) 读取 storage.session[NOTIFICATION_QUEUE_KEY]
// 2) getAll() 获取扩展实际存在的通知 ID
// 3) 去掉不存在的队列 ID；处理仍存在但未记录的遗留 ID
// 4) 将校正后的顺序写回 storage.session
async function reconcileNotificationQueue(): Promise<string[]>;

// 逻辑示意
// clear(oldestId) -> 验证成功/实际不存在 -> 删除对应来源映射
// 若 pendingNotificationClicks 包含该 ID，应保留已开始的正文点击所需快照
async function evictOldestNotification(id: string): Promise<boolean>;

// 逻辑示意
// 使用一个 Promise 链或等效串行器；前一个任务成功/失败后都能释放后续队列
function enqueueNotificationOperation<T>(work: () => Promise<T>): Promise<T>;
```

**具体边界：**

- 应通过扩展 API 的 callback 或兼容的 Promise 包装等待操作完成；每次读取 `chrome.runtime.lastError`。
- 不能只执行 `queue.shift()` 就假设 Windows 通知已经删除；必须确认 `chrome.notifications.clear(oldestId)` 的结果。
- 不能盲目清空 `chrome.storage.session`，只允许删除本通知队列键及对应 `replynotice_origin_<id>`。
- 已有的来源映射由 `rememberOrigin()` 管理，远程通知无原对话映射，不要因此让清理失败。
- 为避免 `onClosed`、`onClicked` 与自动淘汰的异步冲突，修改后要复核事件顺序，不必重写原有跳转状态机。

### 6.3 `entrypoints/background.ts`：统一创建入口（约第 345–403 行）

保留现有函数签名：

```typescript
function createSystemNotification(
  payload: NotificationMessage['payload'],
  sendResponse: (response: { status: string; detail?: string }) => void,
  origin?: NotificationOrigin,
  notificationId?: string,
)
```

保持权限检查不变，将**原有 `chrome.notifications.create()` 的调用及成功回调**纳入串行任务，插入 FIFO 预处理：

```typescript
// 伪代码，不能直接替换完整函数
enqueueNotificationOperation(async () => {
  const queue = await reconcileNotificationQueue();
  const current = notificationId && queue.includes(notificationId);

  if (!current) {
    while (queue.length >= MAX_NOTIFICATIONS) {
      const oldestId = queue[0];
      const removed = await evictOldestNotification(oldestId);
      if (!removed) throw new Error('Cannot free notification slot');
      queue.shift();
      await saveNotificationQueue(queue);
    }
  }

  // 调用原有 chrome.notifications.create(notificationId || '', options)
  // 原有 options 全部保留，包括 requireInteraction 与双按钮。
  const createdId = await createUsingExistingOptionsAndCallback();

  // 相同 ID 更新：保留原队列顺序，不当成新通知淘汰其他 ID。
  // 真正新建成功：将 createdId 追加到队尾。
  if (!queue.includes(createdId)) queue.push(createdId);
  await saveNotificationQueue(queue);

  // 本机通知仍执行 rememberOrigin(createdId, origin, ...)
  // 仍由现有业务回调发送 { status: 'created' }。
});
```

**执行要点：**

- `createUsingExistingOptionsAndCallback()` 是示意占位符，不是仓库现有函数；实际实施应封装或保留**原有 `chrome.notifications.create(..., callback)`**，不得重复发送 `sendResponse`。
- 权限拒绝、创建失败、队列操作失败都要有明确结果，**一次请求只能回复一次状态**。
- 同一远程 `notificationId` 已存在时，可以更新同一通知但不挤掉其他通知；须以 `getAll()` 实际存在为准，不只凭字符串判断。
- 某 ID 从 `getAll()` 消失时，要允许下次正常补位；不能留下死队列导致永久阻塞。
- 不改变原有通知图标、标题、正文、`priority: 1`、`requireInteraction: true` 以及双按钮顺序。

### 6.4 `entrypoints/background.ts`：关闭/清空联动（约第 104–341 行）

- **正文点击**：原有本机通知准确跳转对应聊天、远程通知不导航的语义不变；清除该 ID 后应让 FIFO 下次对账时移除该 ID。
- **左按钮索引 0“关闭”**：继续仅清除当前 ID，不导航；其队列位置应同步失效。
- **右按钮索引 1“清空全部”**：继续执行现有 `getAll() + clear()`，建议与新增通知创建串行调度，避免清空期间新通知被误删或数量失控。清空完成后删除对应队列记录，不清除无关 session 键。
- **系统 X / onClosed**：已有 `byUser` 逻辑保留；系统自动收纳到通知中心时不应因为横幅消失就错误地把仍存在的通知从队列中排除。最终以 `getAll()` 为准。
- **自动淘汰**：删除最旧通知后，除队列记录外也删除该 ID 的原对话来源映射；若已有 `pendingNotificationClicks` 正在读取来源，允许该点击任务完成，避免跳错会话。
- **测试通知**：`CHATGPT_TEST_NOTIFICATION` 也占 1 个名额；不另开旁路。

## 7. 验收与回归测试

| 测试 | 验收标准 |
| --- | --- |
| 从空状态依次收到 1、2、3 | 3 条都可管理，且尽量正常显示横幅 |
| 收到第 4 条 | 先删第 1 条、再创建第 4 条；API 中仅保留 2、3、4 |
| 连续收到第 5、6 条 | 分别为 3、4、5 和 4、5、6；不出现永久阻塞 |
| 极短时间连续收到 5 条 | 串行执行，无竞争造成数量大于 3、乱序或重复回调 |
| 仅剩 2 条时收到新消息 | 直接新增，不误删现有两条 |
| 本机通知 + 跨电脑通知混合 | 共用同一容量，按接收顺序滚动 |
| 同一远程通知事件重复收到（同 ID） | 不误算新名额，不淘汰其他有效通知 |
| 浏览器后台 Service Worker 休眠/恢复 | 能从 session 队列和 `getAll()` 恢复，不依赖单纯内存数组 |
| 初次升级时存在旧版本遗留通知 | 稳定进入最多 3 条状态；无法准确获知遗留顺序时不虚称最旧 |
| 点击通知正文 / 两个按钮 / 系统 X | 原有操作语义不变；队列下次对账一致 |
| 单击“清空全部” | 清理答讯可管理通知，后续再接收新通知正常 |
| 淘汰与正文点击并发 | 不误删其他会话的通知映射，不跳错对话 |
| `clear()` 失败或返回 false | 有错误结果和日志；不静默创建第 4 条 |
| Windows 通知中心 | 被 FIFO 淘汰的旧通知尽量同时从通知中心移除；实际行为以平台实测为准 |
| 系统通知关闭 / Edge 勿扰 | 不应异常创建或无限重试通知 |
| 版本检查 | `wxt.config.ts`、`package.json`、构建 `manifest.json` 和 Edge 均为 **2.0.6** |

**核心验收分两层：** (1) API 可管理通知保持最近 3 条、旧通知先被清除；(2) Windows 桌面实测最新横幅能够出现，不再被 1、2、3 的悬停状态长期阻塞。
