# 答讯 · ReplyNotice — v2.0.4 通知一键清空

## 一、版本与实施范围

- 代码仓库：`LynFrost/Daxun`
- 开发分支：`feature/v2.0.4`（已存在；当前基于 `main` v2.0.3）
- 当前基线：**v2.0.3**
- 目标插件版本：**v2.0.4**
- 需求名称：**通知一键清空**
- 选定方案：**方案 B — 在每条答讯 Windows 通知中增加“清空全部”操作按钮**
- 用户已在当前 Edge / Windows 环境中完成 **通知按钮显示与点击事件** 的兼容性测试，并确认成功。
- 本次交付范围：**仅新增本需求文档并同步 `wxt.config.ts`、`package.json` 两处版本号**；不实施通知功能代码，不修改 `main`。

## 二、背景和目标

v2.0.3 已增加 `requireInteraction: true` 延长 Windows 原生通知横幅停留时间，并在点击单条通知正文时跳转至该 ChatGPT 会话并清除该条通知。

当多个 ChatGPT 回答相继完成，桌面或 Windows 通知中心可能累计多条答讯通知。用户不希望逐条点击关闭，希望**在任意一条答讯通知中点击一次“清空全部”，批量清除当前答讯扩展可管理的所有通知**，无需再打开扩展设置面板。

目标通知内容示意：

```text
答讯 · ReplyNotice
问：这次提交为什么失败？
答：建议优先检查仓库写入授权……
[ 清空全部 ]
```

按钮视觉位置、是否需要展开或悬停由 Edge / Windows 决定；需求指**一次按钮操作**，不承诺始终物理上只需一次鼠标点击。

## 三、交互规则（确定）

| 场景 / 操作 | 期望行为 |
| --- | --- |
| 新的 ChatGPT 回答完成 | 按原逻辑创建通知；每条答讯通知附带“清空全部”按钮 |
| 点击某条通知的 **“清空全部”按钮** | 清理**本扩展当前可管理的全部通知**，不打开 ChatGPT |
| 点击通知正文 | 保留 v2.0.3 行为：跳转对应 ChatGPT 会话，并仅清除该条通知 |
| 点击系统 **X / 关闭** | 仅关闭当前通知，不跳转、不批量清理 |
| 一共存在 5 条可管理的答讯通知 | 点击任一条的“清空全部”，尝试清除这 5 条；其他应用通知不受影响 |
| 没有剩余可管理通知 | 安全空操作，不报错、不创建多余通知 |
| 一键清空后新一轮 ChatGPT 回答完成 | 按原有设置正常发送新通知；一键清空不是“关闭通知”开关 |
| 多标签 / 多会话通知并存 | 只按本扩展通知 ID 清理，不切换任何 ChatGPT 标签页 |
| 扩展自测通知 | 若复用同一通知创建函数，允许同样出现该按钮；不能因此触发测试以外的操作 |

本版本**不增加插件面板“一键清空”按钮**，不增加二次确认弹窗，不实现定时自动清空，也不改变 Windows 通知配置。

## 四、技术实施方案（开发时执行，本次不修改功能代码）

### 4.1 通知增加操作按钮

文件：`entrypoints/background.ts`

现有函数：`createSystemNotification()`；在 v2.0.3 代码中，`chrome.notifications.create({...})` 位于约 **第 186–193 行**。

保持现有的通知图标、标题、消息、`priority: 1`、`requireInteraction: true` 和回调逻辑不变，只在 `basic` 通知的配置对象中新增：

```typescript
buttons: [{ title: '清空全部' }],
```

- 复用已有 `notifications` 权限，通常无须新增权限。
- 不修改问答摘要、提示音、完成检测或去重状态机。
- 用户已验证当前系统可以显示按钮，且点击后会触发 `chrome.notifications.onButtonClicked`（索引 0）。
- 仅把按钮加到答讯通知，不添加第二个无关按钮。

### 4.2 监听按钮点击并批量清空

文件：`entrypoints/background.ts`

在已有 `chrome.notifications.onClicked` 与 `chrome.notifications.onClosed` 的相邻位置注册独立监听器：

```typescript
chrome.notifications.onButtonClicked.addListener((notificationId, buttonIndex) => {
  if (buttonIndex !== 0) return;
  // 使用 chrome.notifications.getAll() 取得本扩展当前可管理的通知 ID
  // 逐条调用 chrome.notifications.clear(id)
  // 对成功清理的通知同步删除对应来源映射
  // 不调用 openChat / tabs.update / windows.update
});
```

**实现要求：**

1. 使用 `chrome.notifications.getAll()` 获取当前扩展可管理的通知 ID；遍历 `Object.keys(notifications)`，不得尝试枚举或清除其他 Windows 应用的通知。
2. 对每个 ID 调用 `chrome.notifications.clear(id)`，处理 `chrome.runtime.lastError` 和返回值。部分失败时记录失败 ID 或数量，继续处理其他通知，不应因单条失败终止整批操作。
3. **清理范围为点击按钮时 `getAll()` 返回的快照**；清理期间新产生的通知不保证被包含，不应因此循环清理新通知。
4. 不通过重复创建通知来展示“清理成功”提示，否则会制造新的待清理通知；可在开发者日志中记录结果。
5. 不调用现有的 `openChat`、`chrome.tabs.update` 或 `chrome.windows.update`；按钮点击应与“通知正文点击后跳转”完全区分。
6. 不假定批量清理时一定触发 `onClosed`，也不依赖 `onClosed` 中的 `byUser` 值完成全部清理。
7. 监听器须在 MV3 后台脚本的正常初始化期间注册，保证 Service Worker 恢复后仍可响应按钮事件。

### 4.3 同步清理通知来源映射

文件：`entrypoints/background.ts`

当前实现以 `NOTIFICATION_ORIGIN_PREFIX = 'replynotice_origin_'` 为前缀，使用 `chrome.storage.session` 保存通知 ID → ChatGPT 会话来源映射；还有 `onClosed`、`pruneOrigins()` 的清理机制。

- 对**成功清除**或确认已经不存在的目标通知 ID，同步删除 `NOTIFICATION_ORIGIN_PREFIX + notificationId` 对应记录。
- 保留 `onClosed` 的既有单条关闭处理，但避免批量清理与 `onClicked` 的异步处理互相覆盖；如发生并发，**已经取得快照的单条点击跳转不得因映射被删除而打开错误会话**。
- 对 `clear()` 失败且通知仍可能存在的 ID，不能随意丢掉来源映射。
- 不误删其他 `chrome.storage.session` 键（例如扩展设置或其他功能数据），不修改保存聊天内容的策略。
- v2.0.3 已有的映射上限 **100 条**、有效时间 **24 小时** 继续保留；本需求不扩展持久化方案。

### 4.4 Windows 通知中心的技术边界

- `chrome.notifications.getAll()` 只枚举**当前扩展可访问的通知**，不等于读取 Windows 全局通知中心的历史记录。
- 对于已被 Edge / Windows 移出扩展通知 API 管理范围的记录，不保证可以查询或清除；即使用户在通知中心仍看到某些历史项目，也不能承诺本功能能全部移除。
- 以实际 Edge / Windows 的 `getAll()` 返回集合与清理结果作为验收依据；不能把“清空系统全部通知”写成成功标准。
- 现有 `requireInteraction: true` 仅请求延长横幅停留，无法保证横幅永不收起；与本需求互不冲突。
- 如果按钮在 Windows 通知中心需要展开后才可见，接受系统自身交互限制，不引入桌面辅助程序或自绘悬浮通知。

## 六、测试与验收标准

在 `feature/v2.0.4` 完成功能代码后，执行 `pnpm build`，并检查 `.output/chrome-mv3/manifest.json` 版本为 `2.0.4`；在 Edge `edge://extensions` 重新加载后确认版本显示为 v2.0.4。

| 测试场景 | 验收预期 |
| --- | --- |
| 新回答完成，单条通知 | 显示“清空全部”按钮；通知正文和问答预览正常 |
| 用户已进行的按钮兼容性测试 | 视为 API 展示 / 点击事件初步验证已通过；仍需回归完整清理流程 |
| 2–5 条答讯通知，点击任意一条的按钮 | 批量清理 `getAll()` 返回的所有可管理答讯通知 |
| 点击按钮后 | 不跳转 ChatGPT，不触发正文点击事件 |
| 点击通知正文 | 仍只清理本条并跳转原会话 |
| 点击通知的 X | 仍只关闭本条，其他条不变 |
| Edge / Windows 通知中心存在可管理通知 | 尝试批量清理；记录哪些通知仍可被 `getAll()` 管理 |
| 仅有一条或没有剩余通知 | 分别正常清理 / 安全无操作 |
| 部分 `clear()` 失败 | 不影响其他 ID 的清理；有错误日志；失败 ID 映射不被无条件删除 |
| 清理完成后检查 session 映射 | 成功清理的通知对应来源映射已删除，不影响无关键 |
| 连续两个不同对话产生通知 | 不串会话，清空按钮不打开错误标签 |
| 清空过程中恰好收到新的回复 | 按调用时快照处理，不对新通知进行无限重复清理 |
| 清空后再次收到回答 | 正常继续弹出通知，系统通知总开关和问答预览开关功能不变 |
| 关闭系统通知总开关 | 保持无通知行为，不受本功能影响 |
| 音效、通知去重、测试通知 | 行为保持正常，不发生回归 |

## 七、明确不做的事项

- 不做插件设置面板的“清空通知”按钮（方案 A）。
- 不清理微信、Outlook、系统更新或其他扩展的通知。
- 不新增本地 Windows 辅助程序、桌面浮窗或原生消息桥接。
- 不增加“确认清空吗？”二次确认；清理仅作用于提醒，不删除任何 ChatGPT 对话。
- 不重构 `entrypoints/content.ts` 的回答完成检测、现有提示音功能或问答内容预览功能。
- 不开发历史通知管理面板，不提供“撤销清理”，也不保证可删除 Windows 通知中心全部历史条目。
