# 答讯 · ReplyNotice — v2.0.2 问答内容预览通知

## 一、版本与开发范围

- 仓库：`LynFrost/Daxun`
- 开发分支：`feature/v2.0.2`（已存在，基于当前 `main` 的 v2.0.1）
- 当前基线版本：**v2.0.1**
- 目标插件版本：**v2.0.2**
- 主题：**问答内容预览通知**
- 开发目标：ChatGPT 每轮回答最终完成后，Windows 系统通知可展示该轮最近一次**提问摘要 + 回答摘要**，并允许点击通知返回对应 ChatGPT 会话。
- 本次范围：需求方案与两个版本字段的同步。**本次文档提交不等于通知预览功能已开发或实测完成。**

## 二、背景与目标效果

v2.0.1 已在 Microsoft Edge + Windows 上实测能够发出“ChatGPT has finished responding.”通知，但不包含是哪条提问、具体回答了什么。

目标通知示例（仅示意内容，实际 Windows 样式、换行和截断由系统决定）：

```text
答讯 · ReplyNotice
问：GitHub 提交为什么失败？
答：主要应排查 GitHub App 的仓库授权和 Contents 写入权限……
```

目标是**预览摘要**，不是把完整聊天内容放入通知，也**不实现通知内直接输入并回复**。标准 `chrome.notifications` 不支持自定义回复输入框。

## 三、功能需求与实施方案

### 需求 1：捕获当前这一轮提问

建议修改：`entrypoints/content.ts`

- 在现有 `onSubmitIntent` / 点击发送 / Enter 提交时，从当前 ChatGPT 输入框读取即将提交的文本并暂存于本轮 `ReplyCycle`；必须在输入框清空前捕获。
- 注意点击发送、回车与 `submit` 可能先后触发；应复用当前提交去重机制，**同一轮只建立一次快照**。
- 只关联本轮提问和本轮回答，不简单读取页面中最后一条历史消息；与原有 `cycleId`、响应周期的开始/结束、路由变化逻辑配合。
- 空白提问、附件/图片提问、DOM 找不到输入框等情况允许降级为“提问内容不可预览”，但**不应影响回答完成通知**。
- 不记录或上报聊天全文到服务器，也不在控制台打印提问正文。

### 需求 2：从完成的助手回复提取回答摘要

建议修改：`entrypoints/content.ts`

- 继续复用 v2.0.1 已验证的助手轮次容器识别：`[data-turn-key]:has([data-conversation-role="assistant"])`，并保留旧选择器回退。
- 在**现有回答完成确认通过后**，从对应助手轮次容器中提取可见的最终回答正文，优先定位正文区域，而不是粗暴地将整个容器的 `textContent` 作为通知内容。
- 排除复制/分享/反馈按钮、隐藏文本、思考细节、工具过程状态、导航标签等非回答内容；保留答案必要的文本内容，不复制整段 Markdown 结构。
- 处理多段落、列表、代码块等文本，合并多余空白；对非常长的内容进行截断，避免通知溢出。
- 建议上限：**提问约 50 个汉字、回答约 100 个汉字**（只作为应用侧默认截取长度；Windows 的实际展示可能更少）。超长添加“……”。
- 未能准确提取回答时回退为“ChatGPT 回答已完成”，不能因此吞掉通知。

### 需求 3：构造系统通知的问答摘要

建议修改：`entrypoints/content.ts`、`entrypoints/background.ts`

- 在现有 `CHATGPT_REPLY_DONE` 消息的 `payload` 中增加当前轮 `questionPreview`、`answerPreview` 以及必要的会话定位信息，保留 `cycleId`。
- 后台使用已有 `chrome.notifications.create({type:'basic', ...})` 创建通知，并将摘要格式化到 `message`；`title` 仍为“答讯 · ReplyNotice”。
- 建议正文格式：`问：...\n答：...`；若系统不显示换行，允许自然截断或采用清晰的单段分隔格式。不依赖 Windows 提供精确排版、完整显示字数或自定义通知尺寸。
- **保留**已有 Windows 权限检查、通知错误日志、重复通知去重、系统通知总开关和 `CHATGPT_TEST_NOTIFICATION` 通道测试。不要将提示音或其他功能一起重构。
- 字段不存在时自动降级为原有完成提示，而不是报错。

### 需求 4：点击通知打开对应的 ChatGPT 会话

建议修改：`entrypoints/background.ts`，必要时调整扩展权限配置（仅限经过核实的最小权限）。

- 收到完成消息时关联该通知的 `notificationId` 与来源 `tabId`、`conversationUrl`。
- 监听 `chrome.notifications.onClicked`；点击通知时优先激活原标签页并聚焦浏览器窗口，标签页已关闭时可以打开原会话 URL。
- 处理同一浏览器多标签、多次连续提问的通知，**不可将所有通知跳转至最后一个活动标签**。
- 注意 MV3 Service Worker 可能休眠：通知来源映射不得只依赖不受保护的瞬时内存；优先采用 `chrome.storage.session` 等最小必要的会话级存储，并清理过期映射。无有效 URL 时安全降级至 `https://chatgpt.com/`。
- 只接受已验证的 `https://chatgpt.com/` 会话地址，禁止使用未经验证的任意跳转链接。
- 不将聊天原文写入持久存储；需要保存的只是通知来源和必要的定位信息。

### 需求 5：隐私设置开关

建议修改：`entrypoints/popup/index.html`、`entrypoints/popup/App.ts`，以及必要的 `storage` 设置读写。

- 新增一个独立设置：**通知显示问答内容**（Show Q&A Preview）。
- 为避免锁屏、共享电脑或投屏时暴露对话内容，**默认关闭**；开启后才显示问答摘要。
- 关闭预览开关时仍保留原先的“回答完成”通知，不改变现有 `System Notification` 总开关。
- 设置保存在扩展现有的 `chrome.storage.local` 设置体系中；只存储开关，不持久保存问题/回答全文。
- 当前轮通知的生成应以后台读取的预览开关状态为准，避免前端发送了摘要就无条件展示。

## 四、版本号同步（必做，不可遗漏）

**本轮目标实际插件版本是 v2.0.2。需要同步以下两个文件，不能只在需求文档里写目标版本。**

| 文件 | 原值 | 修改后 |
| --- | --- | --- |
| `wxt.config.ts` — `manifest.version` | `version: '2.0.1',` | `version: '2.0.2',` |
| `package.json` — `version` | `"version": "2.0.1",` | `"version": "2.0.2",` |

说明：

- 插件弹出面板 `entrypoints/popup/App.ts` 当前通过 `chrome.runtime.getManifest().version` 取得版本，**不需要硬编码改成 v2.0.2**。
- 若版本配置调整后构建工具引起锁文件等变化，应核对实际改动，避免不必要的版本/依赖升级。
- 本文档落地时同步更新上述两处实际版本字段；**通知预览功能本身仍处于待开发状态**，不能仅凭版本号变更宣称功能已交付。

## 五、验收标准

| 场景 | 预期结果 |
| --- | --- |
| `pnpm build` 生产构建 | 构建成功 |
| `.output/chrome-mv3/manifest.json` | `name` 为“答讯 · ReplyNotice”，`version` 为 `2.0.2` |
| Edge 扩展管理页与面板 | 分别显示 v2.0.2 对应版本 |
| 预览开关默认关闭 | 回答完成仍发旧版通用通知，不暴露问答 |
| 预览开启、普通文本问答 | 通知包括本轮提问摘要及回答摘要，且只通知一次 |
| 超长提问、超长回答 | 截断合理，通知能正常发出 |
| 新话题、连续两轮、多个标签 | 问答准确匹配当前轮，不串题 |
| 纯图片/附件提问、回答难以解析 | 能降级提示，不阻断通知 |
| 长时间思考、工具调用 | 不提前通知，仅在最终回答完成时显示一次 |
| System Notification 总开关关闭 | 不发系统通知 |
| 点击不同来源通知 | 打开/切换至对应 ChatGPT 会话 |
| 刷新页面、插件重载、后台休眠 | 不误报；点击来源映射按设计降级或恢复 |
| 通知预览显示 | Windows 可能截断，不能要求与其他原生 Windows 应用通知完全一致 |

- 需求文档包含实施计划，但**本次不编写问答预览的功能代码**。
